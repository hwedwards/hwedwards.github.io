Project / Embedded systems

rocky-telemetry

A small sensor system, built like LEGO: modular C++ firmware for a helmet test rig’s Pico 2 data logger.

The starting point

I’ve been redesigning the sensor system that measures my boxing helmet’s impact response during testing. The basic job is straightforward: read measurements from an IMU and save them to an SD card.

A single data-logger file could handle a small project. But the requirements soon started to grow, making this a useful opportunity to put object-oriented design into practice.

Device behaviour

A button should start and stop recording, and an LED should show what the device is doing. A state machine gives those behaviours a clear home: tracking the operating state and deciding how the device responds.

Each component has its own job and a defined way to connect to the others. That is where the LEGO analogy starts to fit.

Separating sampling
from storage

The design considers a target of 1,000 measurements per second. SD-card writes do not always take the same amount of time, so making every measurement wait for a write can introduce timing problems.

A pool of reusable memory buffers separates those jobs. One core of the Pico 2 can collect measurements while the other writes a previously filled buffer to the SD card.

Architecture reflected in the public firmware. The IMU is configured for 1,000 samples per second; this is not a reported end-to-end logger benchmark.

Hardware & code

The public C++ firmware targets Pico 2, with an MPU6050 IMU connected over I2C and an SD card on SPI.

The button toggles OFF and LOGGING states, with the LED following the current state. Full and free buffer queues let the acquisition and storage tasks pass buffers between the two cores.
